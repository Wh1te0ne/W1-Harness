## 区分模型能力与接口兼容性

模型能力决定能选哪些思考档位；供应商接口决定档位的请求格式及允许携带的附加字段。这两层应分别配置，不能仅凭模型名称认定协议兼容。相同供应商内的不同模型，也不一定支持相同档位。

| 接口 | 思考强度字段 | 配置位置 |
| --- | --- | --- |
| Chat Completions | `reasoning_effort: "max"` | 线路 `api: openai-completions`；模型按需声明 `compat.thinkingFormat` |
| Responses | `reasoning: { effort: "max" }` | 线路 `api: openai-responses`；线路按需声明 `responsesReasoningFormat` |
| Messages | `output_config: { effort: "max" }` | 对应 Messages 适配器；不能直接套用前两种请求字段 |

`default` 表示不在当前选择中指定档位，由适配器、线路配置或服务端的默认规则决定，并不表示低强度或关闭思考。思考强度也不是固定的 token 预算；输出上限、实际推理长度和计费是相关但不同的概念。

## 当前配置与依据

| 线路及模型 | 接口 | 显式可选档位 | 本机兼容配置 |
| --- | --- | --- | --- |
| DeepSeek-Volc / `deepseek-v4-1-flash-261017` | Responses | low、high、max | 线路 `responsesReasoningFormat: effort-only` |
| VX API Default / `deepseek-v4.1-flash` | Chat Completions | low、high、max | 仅该模型设置 `thinkingFormat: deepseek`、`supportsDeveloperRole: false` |

模型上的 `reasoningEfforts` 显式声明如下；左侧是 W1 选择器的档位，右侧是发给服务端的值。未声明的 off/minimal/medium/xhigh 不提供为可选档位，Default 仍保留。

```yaml
reasoningEfforts:
  low: low
  high: high
  max: max
```

火山三档及默认 high 的依据为[火山 DeepSeek-V4.1-Flash 文档](https://console.volcengine.com/ark/region%3Acn-beijing/docs/deepseek-v4-1-flash)，DeepSeek 官方通用说明见[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)。VX 的参数接受情况来自实际接口验证；不能用 DeepSeek 官方默认值代替 VX 的服务端声明。

本机 profile 位于用户目录 `.w1-harness/profiles/desktop/cordis.patch.yml`，对应 `llm-pi-ai.config.providers`。只查配置与凭据引用，不输出凭据正文。VX Enterprise 当前配置没有 DeepSeek 条目；其他模型未套用上述 DeepSeek 映射。三条线路的 `/models` 均返回 200，但未返回可用于声明其他模型思考档位的能力字段，因此不能把目录发现当成能力验证。

## 已发生的故障

2026-10-20，火山模型选择 max 或 xhigh 后收到 HTTP 400，错误为 `InvalidParameter: json: unknown field "summary"`。同一会话切回 Default 后成功。根因是通用 Responses 请求实现同时添加了 `reasoning.summary: auto`，而该火山接口拒绝此字段；并非仅凭此错误就能判定模型不支持 max。

修复在 [adapter.ts](../packages/llm/llm-pi-ai/src/adapter.ts) 和 [config.ts](../packages/llm/llm-pi-ai/src/config.ts)：线路显式设置 `responsesReasoningFormat: effort-only` 时，通过请求载荷回调保留 effort，去掉 summary 及 `reasoning.encrypted_content` include。未开启此配置的 OpenAI Responses 线路保留原行为，其他协议不受影响。实现不匹配火山域名或 DeepSeek 模型名称来暗中分支。

这是供应商线路的 Responses 兼容配置；模型三档声明独立维护。更换接口虽然可能绕过此错误，但会改变请求和历史回放格式，不能未经验证就视为等价替换。

## 排查顺序

1. 确认实际 provider、模型 ID、接口类型及当前会话的思考选择。设置页中的模型名称不足以判断请求协议。
2. 查错误发生位置：`UNSUPPORTED_REASONING_EFFORT` 可能在本地校验阶段出现；HTTP 400 `unknown field` 表示服务端拒绝字段；401、限流和超时应分别排查，不能统归为思考参数问题。
3. 对照实际请求字段、模型 `reasoningEfforts` 映射及线路兼容项。特别检查 Responses 的 summary/include，和 Chat Completions 的 thinking 开关、reasoning_effort。
4. 分别用 Default、low、high、max 做短请求，再验证工具调用与结果回传。简单回答成功不代表旧会话历史或工具链回放一定兼容。
5. 核对运行版本。候选测试通过、配置保存、更新包 prepared、更新 applied、日用 Host ready 是不同状态；启动与更新入口见[开发与上游维护](开发与上游维护.md)。

会话日志位于用户目录 `.w1-harness/sessions/`，当前格式为多帧 `session.v4.jsonl.zstd`；按仓库的 Zstandard 帧扫描器逐帧读取。排查只提取 `request/header` 的配置、`model/selection` 和错误状态，避免导出聊天内容或认证信息。单次解压只读到首帧不能作为日志为空的证据。
