最近更新：2026-10-18。产品名称：W1 Harness。当前阶段：本机开发版持续迭代，回复建议已接入；首版安装验收见[首版构建与验收](首版构建与验收.md)，当前开发进展以[工作记录](工作记录.md)为准。

本文件是定制 Harness 需求与待办的主要维护位置，承接原插件工作区的“定制Harness规划”。原位置保留导航，不再维护副本。

## 目标与范围

基于 DSH 开源代码维护独立桌面产品，保留上游产品理念及可复用能力，支持用户自己的品牌、工作组织和操作体验，并持续吸收有价值的上游更新。

第一阶段聚焦 Windows 本地桌面。Android 远程客户端与 NAS 中继已纳入范围；自有账号系统、云端执行引擎和多人协作不属于本轮范围。

## 用户已提出的需求

- 独立名称 W1 Harness；独立目录与项目说明。
- 品牌图标采用用户选定的 D / Fold 方向；标准资产与使用规则见 [W1 品牌规范](W1品牌规范.md)，运行时与安装器接入归入 H-02。
- 不以 DSH 官方账号登录作为进入工作区的前提；不提供官方账号余额入口或后台查询，保留模型 API Key、用量和费用统计。
- 持续跟踪上游 Alpha、RC 和正式发布，自动检查并提醒，省去用户每天查看 GitHub；用户在开发聊天中主动发起跟进，再评估、合并、验证和发布。应用不自动合并代码或安装更新。
- 项目可以独立命名并关联多个源文件夹，具有“主要／设为主要”角色；聊天按项目归属，不再以单个目录作为项目身份。主要目录负责默认执行、Git 与项目规则入口，其他目录仍为可访问的项目资源，不按模型注意力权重划分。
- 具备日常可用的浏览器操控体验，先评估已有 DSH 能力及缺口。
- Android 手机通过公网中继连接电脑，不依赖同一局域网；扫码确认后长期绑定，查看同一份会话、状态并发送消息。中继公网入口由用户指定为 `https://w1hrelay.whiteone.cn:8112`，NAS 服务端口为 `28981/TCP`。
- 输入框提供灰字回复建议，主模型自动选择建议模型；Tab 填入后由用户确认发送。

“独立项目”“当前执行目录”和“访问权限”必须分别建模。移除目录关联不删除文件，项目改名不修改磁盘目录。关联多个仓库时，每次 Git 操作仍需确定目标仓库。

## 项目模型与主要目录

2026-10-16 用户确认采用“多个源文件夹，其中一个主要”的逻辑。目录角色区别影响默认操作入口，不表示其他目录只读、不可执行或模型关注权重较低。Codex 已确认行为和未实测范围见[资源与决策](资源与决策.md)。

- Project：稳定 ID、显示名称、folderRoots、primaryFolderId、项目配置；目录用稳定记录 ID 引用，路径不作为项目唯一身份。
- 存在目录时必须且只能有一个主要目录，primaryFolderId 必须引用项目内的目录；无目录时为 null。
- Session：显式关联 Project，另行记录 cwd 和目标仓库。新聊天默认在主要目录启动；显式切换任务目录不改变聊天归属，也不自动扩大权限。
- 所有关联目录参与授权范围内的搜索、读取、编辑与文件选择。默认 Git、PR 和 worktree 操作指向主要仓库；对其他仓库的 Git 操作需有明确目标，不把仓库混为一个。
- 规则发现：主要目录承担默认项目规则、技能和项目配置入口；访问其他目录时按其作用域读取适用的 AGENTS.md 等要求，不把所有目录的规则无差别合并为全局配置。
- 无目录项目：需要文件产物时使用明确的应用管理任务目录，不强迫用户先选文件夹。
- 旧项目迁移：将原单目录映射为唯一主要目录，保留项目和会话身份；添加第二个目录不自动换主目录。
- 浏览器存储：项目身份、浏览器分区与执行 cwd 分开考虑，避免切换主要目录或任务 cwd 导致登录态错配。

### W1 切换规则与验收

2026-10-17 已实现项目编辑、稳定归属与新会话主要目录默认值；以下多仓库专属视图和跨目录规则冲突专项仍待实现或验收，不能据此声称 Codex 的实现已经实测。

1. “设为主要”只修改项目默认入口并持久化，不移动文件、改目录名或变更聊天归属；其他源文件夹继续保留。
2. 切换后新建聊天使用新主要目录；已有聊天及正在运行的终端/进程保留原执行位置，只有显式切换才改变后续任务目录。
3. 移除主要目录时要求选定替代目录，或明确移除全部目录；不静默改指其他目录。主要目录失联时显示不可用状态，不偷偷回退到另一个仓库。
4. 关联范围、目录读写权限、当前任务 cwd 分别展示和验证；“设为主要”本身不能提升权限。
5. 两个独立 Git 仓库同属一项目时，修改视图能区分仓库，默认 PR/worktree 目标明确；主要目录非 Git 仓库时，不猜测另一个目录作为操作目标。
6. 验证目录改名/移动、去重、主目录切换、应用重启、旧会话恢复及规则冲突，确保配置、权限和 UI 一致。

## 已核查的上游能力

2026-10-16 核查的源码已固定为 `dsh-v0.2.1-alpha.4` 基线。以下为静态能力核查，原版启动验证另见运行文档。

- 浏览器操控已有 Playwright MCP、Chrome DevTools MCP、Stagehand 实验性提供方，需要显式启用；同一注册服务仅允许一个提供方。
- 右侧浏览器是用户可见页面模块，不注册模型工具；让 Agent 操控同一个可见标签页需要单独整合验证。
- 外部浏览器 attach 需要调试端点；现有浏览器状态可复用，但聊天恢复不等于恢复浏览器状态。
- Workspace 已有标题和改名能力，但仍以单一路径去重并校验会话归属。
- 修改会话当前目录不自动改变项目归属和沙箱可写根。

本轮及前次核查均未启用浏览器后端，以上不代表本机已可用。源码来源与文档链接见“资源与决策”。

## 上游发现与开发跟进

2026-10-16 用户明确要求持续跟随上游，但开发跟进由用户在 Codex 等开发聊天中发起。固定源码基线用于可复现构建，不表示停止发现新版本，也不表示只关注 RC 或正式版。

H-07 的首版行为：

- 应用启动后异步检查，持续运行时默认每 24 小时检查一次，并提供手动刷新；失败不阻塞使用，显示最后成功检查时间和检查失败状态。关闭应用期间是否另设系统级检查，待单独决定。
- 读取上游发布列表，覆盖 Alpha、RC 和正式版；记录当前 W1 版本、已整合的上游标签，以及新发布的标签、日期、说明和来源链接。上游源码发布与 Windows 安装包发布分别标明。
- 发现新发布后提醒一次，并在应用内保留“待跟进”；已查看、暂缓和已整合是不同状态。用户暂缓后仍可重新查看，多个新版本可以集中评估，不反复弹同一提醒。
- 提供“复制升级任务”：包含当前基线、目标标签、发布说明、需要保留的 W1 定制功能，以及合并和验证要求，方便用户粘贴到开发聊天。检查器不自动创建开发任务，也不向其他聊天发送指令。
- 用户发起跟进后，由开发流程比较完整差异和功能重叠；合并验证完成并记录新基线后，才把目标标为已整合。发现、查看通知或开始开发都不能冒充升级完成。

首版已实现检查、提醒、暂缓和复制升级任务，验证状态见[首版构建与验收](首版构建与验收.md)。实际合并与交付步骤见[开发与上游维护](开发与上游维护.md)。
