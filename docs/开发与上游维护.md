源码已经在根目录接入完整上游 Git 历史，基线及运行方式见[原版构建与隔离运行](原版构建与隔离运行.md)。初始化资料的原始副本和哈希保存在 `.work/bootstrap-original/`；上游 README 与 AGENTS 保留，并加入 W1 导航和执行范围。

## 本机快速迭代

日常入口为桌面和开始菜单中的“W1 Harness”，都指向 %USERPROFILE%\.w1-harness-app\W1 Harness.exe。启动器使用现有 Fold 图标；快捷方式直接引用同目录的 w1-app.ico，安装脚本通知 Windows 刷新这两个快捷方式。启动器隐藏 PowerShell 窗口并调用 scripts/w1/Start-W1.ps1；Windows 任务栏重开命令也指向同一 exe。启动复用带 W1 内嵌名称与图标的独立 Electron 副本、既有 Node/Python/Office 和开发包链接，不运行构建、打包、安装或运行时 smoke。首次缺少已准备资源时会报错，不静默进入完整发布流程。日常启动通过 start-prepared.mjs 读取现有桌面与 Host 构建，正常情况下不加载 tsx 和开发准备依赖，也不经过 pnpm run。修改依赖后按变更范围安装/更新依赖；应用版本、Host 协议、pnpm 或 Electron 内置 Node 版本变化时，正常退出后的首次启动回到原开发脚本刷新项目链接；同版本依赖变化需要刷新时使用 -RefreshProject。缺少运行时或构建产物仍报错，不隐式打包。调试端口默认关闭，只有显式 -DebugPortBase 才启用。

安装或修复入口时，在项目根目录运行 `pwsh -NoProfile -File scripts/w1/Install-W1Launcher.ps1`。该命令准备可复用的 W1 桌面运行程序、编译小型启动器并写入当前用户的快捷方式；同名旧 W1 快捷方式先备份到 %USERPROFILE%\.w1-harness-app\backups。旧安装包本体保留，但开始菜单的 W1 入口改为当前开发版。运行后可右键快捷方式或运行中的 W1 图标选择“固定到任务栏”；入口修复脚本会同时备份并更新已有的 W1 任务栏快捷方式，不修改其他应用的固定项。任务栏重开信息在 W1 下次正常启动时生效。

Windows 的 MSIX AppData 重定向会让开发工具与桌面程序看到不同的文件，所以启动器固定在用户目录下的 .w1-harness-app，不放在开发工具私有 AppData 中。运行时在当前用户的实际开始菜单中补齐 W1 入口；日用开发版统一使用 local.w1.harness.dev 作为 Windows 应用身份，不沿用旧 Electron/安装候选的分组记录。重命名的专用程序仍显式使用开发运行路径，不启用打包版的资源查找或自动安装。shell/<Electron版本>-<标识>/W1 Harness.exe 是原 Electron 的独立副本，写入 W1 名称和 Fold 图标，原 node_modules 不修改；应用代码仍从本仓库的现有构建产物加载。只在 Electron 版本、图标或应用名称变动时重新准备该副本，日常启动只检查缓存；程序首次准备约 1.8 秒。

启动器依赖当前项目目录、已准备的运行时和本机 Node/PowerShell，不是可单独搬走的便携包；移动项目后重新运行安装脚本。日常局部构建不重建启动器。每次启动分别写入 .work/local-dev/desktop-<时间>-<进程>.log，启动器的报错日志位于 %USERPROFILE%\.w1-harness-app\logs；不再覆盖同一个正在写入的 desktop.log。启动失败会显示日志位置。

长期数据位于 %USERPROFILE%\.w1-harness，Electron 设置位于 %APPDATA%\W1 Harness。启动时仅在缺少文件时创建 .w1-harness\AGENTS.md；现有内容不覆盖。DSH_AGENTS_HOME 固定为 .w1-harness\agents，全局规则和技能不再默认继承用户共享的 .agents；项目内 AGENTS.md 仍按实际项目读取。共享目录仍保持隔离；用户明确授权的数据导入采用独立副本，见下方迁移记录。

在项目根目录使用以下定向命令：

```powershell
# 默认更新品牌模块，也可指定另一个 packages/ 下的模块
node --import tsx/esm scripts/w1/build-local.ts packages/client/ui-brand-official
# 修改桌面主进程后构建并正常重启 W1
node --import tsx/esm scripts/w1/build-local.ts desktop
# 仅修改网页入口、主题字体等公共静态资源时
node --import tsx/esm scripts/w1/build-local.ts shell
```

客户端插件构建会触发现有 Host 的资源更新通知；本轮已验证运行中的字标自动更新，无需重启或安装。Host 和桌面主进程变化需要正常退出再打开开发入口。一般修改仅做对应模块的类型、构建或行为检查；不默认运行完整 build、doc-sync 或安装卸载循环。

本轮测量：桌面入口局部构建 6.5 秒，品牌模块初次构建 4.0 秒、后续字号微调 1.3 秒；后者已在实际 Electron 窗口自动生效。这些是当前机器本次记录，不承诺所有模块都同样耗时。构建记录和开发日志在 .work/local-dev/，不入 Git；日志摘录需移除本地 Host 临时认证参数。普通启动与已安装旧 W1 使用相同的 W1 数据和单实例锁，日常只使用开发版入口。

## 任务栏启动与唤起

任务栏固定项、桌面和开始菜单统一指向用户目录下的 W1 Harness.exe 启动器。install-shortcuts.cjs 支持 --taskbar-only，仅修复已有 W1 固定项，并保留 ToastActivatorCLSID 等未修改属性；备份放在 .w1-harness-app/backups。

W1 专属 Electron 副本的 resources/default_app.asar 提供无参数入口：旧固定项直接打开该程序时，也会转交日用启动器。原始加载器保存在同目录的 w1-electron-default.asar，带应用路径的开发启动仍使用原参数解析器；prepare-windows-entry.mjs 校验归属和哈希，重复启动不重写，不修改 node_modules 内的 Electron。

已运行 W1 时，Start-W1.ps1 通过相同的 Electron、用户数据目录和应用路径发送单实例唤起请求，跳过迁移及开发启动准备；冷启动继续使用完整检查。W1 主窗口在启动页准备好后显示，不等待 Host 完全就绪；登录流程遗留的窗口唤起拦截已移除。桌面代码改动仍需正常退出后重开生效。

冷启动和已有实例唤起统一通过 run-logged.mjs 启动并等待子进程。stdout/stderr 直接继承日志文件句柄，不依赖 PowerShell 的输出管道；旧实例正在退出、唤起进程接管成为新主进程时，也保留完整生命周期。日志句柄在 spawn 后由子进程独立持有，避免启动器输出读取端关闭触发 EPIPE。

2026-10-19 定向验证：入口归属和幂等性 3 项、单实例和任务栏 8 项通过，桌面类型检查和局部构建通过，构建约 10 秒。通过实际固定项启动后 Host 正常监听；再次启动使用直接唤起分支，主进程 PID 保持不变。用户要求不用 Computer Use，最终窗口可见性、任务栏点击效果由用户验收；未强制重启正在运行的 W1，也未修改原 DSH。

退出等待以 Host 的进程 exit 事件为准；日志流 close 只用于收集完整崩溃诊断。独立插件子进程可能继续持有输出句柄，不能因此把已经退出的 Host 当成仍在运行，并额外等待 10+5+5 秒。2026-10-19 的隔离复现验证了该区别；当前开发构建已修正，真实重开耗时待用户下一次正常退出后观察，冷启动仍需加载运行时和插件，不运行构建。

## 冷启动准备与计时

Start-W1.ps1 只在项目数据仍为 v2、或 profile 还声明旧用量/通知插件时调用对应迁移脚本；正常 v3 项目不再启动三个空跑的 Node 迁移进程。当前格式与必要文件检查仍保留。prepare-windows-shell.mjs 每次核对归档哈希，但只在需要更新归档时加载 asar 构建库。

prepared-project.mjs 对比应用版本、Host 协议、pnpm 和 Electron 内置 Node 版本。内置 Node 版本探测保存在 .work/local-dev/launch-cache，以 Electron 的真实路径、大小和修改时间区分；执行文件改变后重新探测。这里只缓存版本探测，不缓存业务配置、会话或 API Key。

仅做准备、不打开窗口时可用 Start-W1.ps1 -PrepareOnly；该模式仍可能执行必要的迁移或刷新链接，不是通用只读模式。直接比较开发准备器时，可分别运行 node --import tsx/esm apps/desktop/scripts/dev.ts --skip-build --reuse-runtime --reuse-project --prepare-only 和 node scripts/w1/start-prepared.mjs --prepare-only。

2026-10-19 同机三次测量：原开发准备器 1317/1280/958 毫秒，快速准备器 62/57/60 毫秒；运行程序检查 424→64 毫秒。新 PowerShell 完整准备模式一次为 1180 毫秒。此处不包含 Host、插件与会话界面加载，也不是系统重启后的磁盘冷缓存测量；不能据此宣称完整应用几十毫秒启动。

启动日志中的 [w1-startup] 依次记录 prepared、main-loaded、electron-ready、window-ready、host-start、host-ready、workspace-shown 等实际发生阶段；elapsedMs 从 Start-W1.ps1 开始计算，阶段顺序随异步准备变化。只含阶段名和时间，不含会话和认证信息。完整日常启动体验由用户验收，后续可据此定位剩余等待。

## 开发规则

- 保留 DSH 插件化框架和可复用服务；修改核心接口前，先查上游扩展方式。
- 自定义功能保持明确边界；项目模型需要协调存储、会话、权限与 UI，不能仅修改显示标签。
- 不降低认证或权限来实现免账号使用；DSH 账号、模型凭据、本地服务认证分开处理。
- 测试数据自行生成，不复制真实会话、账本、浏览器登录态或密钥。
- 文件内不硬编码个人密钥；配置示例只含占位值。
- 修改既有代码时记录行为差异和验证；仅文档修改做回读与链接检查。
- 不触碰官方已安装文件或现有插件的不可变发布目录。

## Git 与上游同步

- upstream 指向 https://github.com/deepseek-ai/deepseek-harness.git；origin 待自有远程确定后配置。

- 开发分支默认使用 codex/ 前缀；不要把不同功能、真实用户配置和构建缓存混为一次提交。

- 对外分发时保留 MIT 版权、许可和第三方声明，明确基于 DSH；使用 W1 自己的品牌身份。

## 更新流程

1. 自动发现上游 Alpha、RC 和正式发布，并提醒用户；检查触发、通知状态和开发任务交接以[项目规划](项目规划.md)的 H-07 为准。此步骤不改变源码基线或本机程序。
2. 用户在开发聊天中发起跟进并指定或确认目标版本后，在独立分支比较当前基线与目标标签；可集中跟进多个发布，保留可识别的 W1 定制提交。
3. 列出新功能、修复、接口变化、数据迁移和与 W1 功能重叠的部分。
4. 合并并解决冲突；代码无冲突仍需验证行为。
5. 完成变更范围内的检查及本机开发版验证，记录新的上游基线与验证范围；未完成验证的候选仍标为待跟进。
6. 仅在用户明确需要安装包或分发时，另行执行完整打包和相应安装验证。

删除被上游替代的定制功能前，验证原有配置与历史数据能迁移。应用版本回退与数据恢复分别验证，不假设旧程序一定能读取新版数据。
